# 系统研究方法、文件定义与质量要求

## 1. 研究对象与名词边界

- **上游资料（source）**：Fork 中原始代码、原始 README/ARCHITECTURE/AGENTS、官方文档、ADR、Issues、测试、工作流；均是证据或作者意图，不自动成为研究权威。
- **研究基线（baseline）**：明确仓库+commit+时间，确保同一结论基于同一版本；其他仓库独立锁定。
- **业务对象（business object）**：真实业务语义及规则；不能简单等同于 ObjectStack ObjectSchema 数据定义。
- **角色（role）**：区分人员岗位/业务参与者、流程角色、授权集合、执行身份、组织/租户作用域。
- **架构（architecture）**：系统构成、关系、重要决策和质量属性；不能以包目录充当全部架构。
- **详细设计（detailed design）**：具体类、接口、结构、状态、算法、并发、事务、异常/恢复与实现契约。
- **机制研究（mechanism study）**：解释对象在什么条件和边界上如何工作，包含替代方案、异常和反例。
- **经验/可复用候选**：可迁移的知识，不因被研究或被写入文档自动变成规范、生产能力或代码资产。

## 2. 输出文件职责

- README：只负责总目标、入口、六种成果的职责和定位。
- AGENTS：只负责研究执行边界、写入纪律、真实性与质量行为要求。
- PLAN：只负责研究阶段、状态、任务顺序和验收条件。
- METHOD：只负责术语、来源、证据分类、研究方法、质量准则及标准映射。
- TEMPLATES：只负责产物最小表达形式，不重复方法和标准解释。
- DESIGN：只负责研究对象关系、整体路线、成果消费与可演进的设计决策，不复制当前执行台账。
- BASELINE：只放已核查的仓库快照、原始入口、未决证据与初始审计记录。
- reports/：六个独立研究成果，按 README 的职责划分；研究过程中若发现无法维持边界，优先修正职责，而非复制内容。

## 3. 证据类型与结论强度

| 类型 | 可以证明 | 不可以据此证明 |
|---|---|---|
| 作者声称/官方文档 | 开发者目标、对外说明、声明的契约 | 实现存在或无 Bug |
| Schema/声明与实现源码 | 类型存在、实现逻辑、可追踪路径 | 所有入口均调用、实际执行成功 |
| 测试代码 | 预期行为和存在某些检验条件 | 测试已运行/覆盖真实系统全部行为 |
| 测试执行记录 | 在指定 commit/环境/参数下通过或失败 | 其他环境必然正确、生产安全 |
| 真实运行观测 | 在具体环境观察到输入、输出和副作用 | 所有用户/租户、异常路径都正确 |
| 跨项目与标准比较 | 机制取舍、适用假设和风险推断 | 尚未测量的成本收益或“ISO 认证” |

证据记录最小字段：**主张、证据类型、来源仓库/commit、路径及函数/行、实际观察、解释、反证或限制、未验证部分、结论状态**。可用稳定 URL：
https://github.com/scbdzhwl/objectstack-analysis/blob/<commit>/<path>#L<start>-L<end>
（占位符应替换为真实 commit 与可验证行；路径或行移动则更新。）

## 4. 源码研究步骤

先系统问题与对象→定位真实消费者→依赖图及调用入口→参数/契约/权限→状态变化→持久化及事件→异常/重试/补偿/幂等→返回值与外部可观察结果→测试与缺口→提出替代解释和反例。

不可用仅凭 grep 出现次数代替完整调用覆盖；必须说明检索范围和未覆盖路径。业务规则若仅来自源码，应标注“实现所呈现的规则”，不得伪称官方正式业务需求。

## 5. 标准与专业参考的正确用法

标准是**关注点与质量审查坐标**，不是要求 ObjectStack 实现所有条款或满足认证：
- ISO/IEC/IEEE 42010：利益相关方、关注点、视图/视角、一致性、架构决策。
- ISO/IEC/IEEE 29148：需求、功能行为、约束、验证性与可追溯。
- ISO/IEC/IEEE 15289：文档信息项职责，可按需要合并/拆分。
- ISO/IEC 25010：功能适合性、性能、兼容、交互、可靠、安全、维护、灵活性与安全相关质量。
- ISO/IEC/IEEE 12207、15288：软件/系统生命周期过程、验证、维护和演进。
- DDD、契约设计、模块化、数据一致性、威胁建模、性能工程：用于解释机制与代价。

引用具体标准条款、版本或声称符合标准前，应查其现行官方版本及可见的原始条款；不得凭本研究摘要推定认证。评估现有设计与上游实现时须采用**相同问题、条件和质量属性**。

## 6. 研究知识类型、迁移与历史因果

专业内容类型至少涵盖：系统/产品功能、业务语义/角色/流程、架构、程序与算法、数据/接口/契约、质量与安全、历史事件链和失败根因、测试与实现资源。不同类型可在一条完整机制中关联，不强制每种类型单独建文件或赋予同一证据等级。

**历史演进**以问题/能力事件为单位，允许跨多个提交、Issue、分支和 ADR；逐项区别“实际改了什么/为什么作者说要改/我们根据证据推测的原因/引入或修复了什么/后来怎样验证”。不能用提交消息或一次 diff 自动说明因果，也不能把代码风格好坏等同于业务质量。

**迁移资源**至少回答：哪个目标任务的什么问题；怎么用、输入输出和失败条件；作用的系统层次、依赖及维护位置；原来源/版本/许可；证据和未修复缺陷；怎样在目标环境检查适用、兼容性和效果。没有真实消费者时可以保留研究成果，不能随意认定已采用。

## 7. 证据成熟度与专业深度分离

| 状态 | 允许声称的事实 | 不可越级推断 |
|---|---|---|
| G0 范围固定 | 来源、commit、范围和未读部分已明 | 功能已完整掌握 |
| G1 事实采集 | 有可核查实现、差异或声明证据 | 机制可靠与已测试 |
| G2 机制审查 | 具体路径、条件、反例和质量取舍已分析 | 实际运行成功 |
| G3 本地验证 | 指定环境和版本下测试/复现确有记录 | 生产可靠 |
| G4 运行观察 | 有准确运行版本、真实输入/输出与系统证据 | 可直接迁入新产品 |
| G5 利用收益 | 目标任务的实际采用、验证和投入/质量反馈可追溯 | 所有场景都成立 |

A/B/C 表示研究叙述的事实恢复、机制解释、可迁移深度，见 DESIGN §4；P0–P5 则是 PLAN 的工程阶段。**三组坐标不得相互替代**；并非所有问题都需要走到 G5。

## 8. 研究质量门槛

1. **完整性**：覆盖业务/角色/功能、静态架构、动态行为、质量与生命周期，不以源码文件多代替覆盖率。
2. **正确性**：事实/推断/假设/未知分列；能指向实现和消费者；无虚构运行结果。
3. **关系性**：对象→行为→状态→契约→模块→测试→外部影响，关键关系明确。
4. **对抗性**：寻找反例、失败路径、旧版本变化与替代解释；不得只验证预期结论。
5. **适用性**：给出场景、前提、资源、质量、迁移和学习成本；避免脱离智慧城市专业边界。
6. **可维护**：更新已有责任文件，保留原证据；索引、状态、引用一致；避免为同义概念另建文件。

对实质成果发布前，至少检查一次**资料覆盖、内容与源码一致性、交叉文档重叠、结论状态、证据链接及未完成事项**。无实际验证时只可写“静态研究结论/待证实”。
