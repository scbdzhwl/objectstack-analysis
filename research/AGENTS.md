# AGENTS｜ObjectStack 研究专属规则

**适用范围：research/ 下的研究、分析、记录、计划和报告。**
本 Fork 的根 AGENTS.md、docs/NORTH-STAR.md 及上游其他规则是需要阅读、辨别和引用的**上游资料**，不直接决定本研究工作的目标、文档权威和交付状态。使用 Codex/其他 Agent 时应显式指定“先读 research/AGENTS.md 与 research/PLAN.md”；不同工具对嵌套 AGENTS 的自动生效行为须实际核验，不能仅因文件存在便宣称已生效。

## 目标与约束

- 本任务是**科学研究与软件工程分析**，不是维护上游 ObjectStack、增加功能、修复 Bug 或选型推销。
- 保留完整上游 Fork 的文件、提交、文档与规则作为原始研究资料。**仅修改 research/**；若需改源码、根 AGENTS 或上游文档，停止并提出独立变更理由和审查任务。
- 六项产物的职责、索引见 README；研究阶段与门禁见 PLAN；证据规范与质量标准见 METHOD；格式见 TEMPLATES。已有定义不得复制产生平行规则。
- 从是什么、为什么、系统位置、前提、机制、实现、失效路径、适用/不适用情况和关联设计深入；尊重真实业务，不用抽象目录代替业务规则。
- 不预设上游合理，也不预设本公司的 DES-ARC 合理；允许保留、改进、放弃、待验证、反向推翻原有假设。

## 每个分析任务的必要步骤

1. **定位**：说明待回答的问题、系统边界、涉及的功能/模块/业务行为和应当看的直接来源。
2. **取证**：记录仓库、完整 commit、文件路径、函数/结构或行范围、设计文档、相关测试及必要的 Issue/ADR。区分本 Fork、上游最新、HotCRM 和其他项目版本。
3. **恢复机制**：沿入口→契约→执行→存储/副作用→输出→失败路径追踪，不用类名/注释代替真实调用。
4. **验证结论**：区分作者声明、源码存在、测试代码存在、测试执行通过、运行观测、分析推断、尚未知晓；记录矛盾和反证。
5. **工程评价**：描述问题与约束、替代方案、成本/质量权衡、场景限制和迁移风险；ISO 标准用于评价关注点，不宣称未经审计的合规。
6. **交付检查**：核对来源覆盖、内部一致性、引用能打开、无未证实的完成声明、与其他成果职责不重叠，更新 PLAN 的实际状态。

## 禁止行为

- 不把官方 README/ARCHITECTURE/AGENTS/ADR 的文字直接当实际实现结论；不把 tests 存在写成 tests 通过。
- 不因找到一个实例或一条路径便宣称覆盖全部对象、调用入口、角色或租户边界。
- 不自动编造业务语义、角色职责、权限结论、性能和成本数字。
- 不盲目复制上游的开发项目治理体系，也不新建独立的全公司规范、SSOT、架构层级、Engine、Registry。
- 不用模型总结替代源码取证；不因为长报告/漂亮图表就宣称完成研究。
- 不将客户数据、秘密、凭据提交到公开仓库；不要在取证测试中使用生产环境。

## 修改权限与运行实验

- 默认只读分析上游；报告、索引、计划、检查结果仅提交 research/。
- 编译/运行/PoC 是为消除关键不确定性，按需最小化；须先确认环境、启动命令、数据隔离、依赖、资源限制，记录真实命令、退出码和产物。
- 研究分支提交后建议经 PR 审核再合并；没有代码执行证据不得把结论升级为“运行已验证”。

## 输出格式

中文主体、英文源码标识保持原文。先结论后证据和机制；图仅用来准确表达依赖/结构/时序/状态；优先 Markdown + Mermaid，重要技术结论须有永久源码链接。默认简洁，但不能牺牲完整性。重要术语首次解释；已验证、推断、待验证必须显式可辨。

> 冲突处理：本研究的方向及研究文件职责以用户明确目标、research/README、research/PLAN、research/METHOD 为准；运行或修改上游程序时，则尊重其构建/安全约束，但不得将上游维护优先级自动迁移为本研究目标。
