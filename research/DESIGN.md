# ObjectStack 系统研究、知识恢复与工程利用总体设计

> 身份：研究项目的总体设计（review draft；非公司规范、非官方 ObjectStack 架构、非已经实施的知识平台）。
> 首次形成：2026-11-15。研究源码基线详见 BASELINE.md；执行状态、下一批任务详见 PLAN.md。
> 输入：本项目关于“寻找探宝”、分析利用、代码资产演进、ObjectStack 系统/ISO 研究与 2026-11-15 两轮反向审查的明确要求。历史部分资料在其他会话或文件库，不假定 Work 已直接读取；本文件保存经过本轮综合的**设计判断和仍待验证的假设**，原来源可得时需要继续对照。

## 0. 本次设计裁决摘要：为什么必须有本文件

之前的六文件已建立研究入口、计划、证据类型和六份报告的职责，但**缺少研究对象如何构成知识、知识如何被下次任务找到与使用、事实和可用资产如何相互追溯的总体方案**。

ObjectStack 研究包含两个同时成立的目标：

1. **学术与工程理解**：系统级、业务级、架构级、程序级研究成熟系统，解释是什么、为什么、如何形成、放在哪、怎样实现、前提、差异、失效及长期演进。
2. **工程能力转化**：从源码与历史提取事实、机制、契约、反例和资源，准确用于需求、架构、设计、编码、测试和维护，降低重复摸索与错误，并以真实消费者反馈修正知识。

研究、设计、取证、编译、运行、采用与效果验证都可以产生价值，但属于**不同完成状态**；PoC 只在关键不确定性需要实证时使用，不是主目标。

## 1. 对象、权限与边界

- **上游 ObjectStack Fork**：全部源码、原 AGENTS、架构文档、测试、ADR、Issues、示例、版本历史都是研究资料和可能的作者约束，不能自动当作已证实的系统行为或本项目指令。原文件不改动。
- **外部参考**：HotCRM、ObjectStack Docs、Java 项目、工程标准、旧系统/前后端及 DES-ARC：分别锁定来源、版本、许可和可读取范围。若只取得历史 L0/L1，不冒充最新 DES-ARC 的事实。
- **研究成果**：仅在 research/ 中维护研究设计、计划、证据索引、报告和候选资源；有效事实与判断有明确出处、层级和版本。
- **目标消费者**：一个明确的设计、开发、测试、维护或学习任务；实际生产代码、正式契约与架构仍由其自己的权威仓库维护。
- **权限边界**：研究结论不自动批准业务规则、公司规范、架构变更或第三方代码复制；需许可、责任、适配及目标项目验证。

不能照搬跨项目“分析利用”工作区的目录与治理。它提供通用价值链和边界，本设计只实现 ObjectStack 专项研究的职责；未来可以把经过核验的成果输出到已有分析利用体系，而不是创建第二套全公司知识库。

## 2. 核心信息关系：不是六篇孤立的文章

~~~mermaid
flowchart TB
    S["Source：代码/文档/测试/历史/运行"] --> E["Evidence：固定版本与定位"]
    E --> F["Fact：对象、行为、契约、实现及限制"]
    E --> H["Episode：问题/设计演进/修复因果"]
    F --> A["Mechanism & Finding：机制解释、质量、反证"]
    H --> A
    A --> R["系统级专业报告"]
    A --> K["Knowledge Candidate：可迁移知识与负面经验"]
    K --> U["Consumer：需求/架构/程序/测试/维护"]
    K --> X["Resource：契约/样例/测试/工具/适配实现"]
    X --> U
    U --> O["Trial/Outcome：采用位置、验证和实际结果"]
    O -.更新适用边界或淘汰.-> K
    O -.新反证.-> A
~~~

这些是**逻辑关系**，不要求创建 Source、Episode、Candidate、Outcome 六类文件、数据库表或 Agent。简单研究结果可以直接在报告里表达；当知识被多任务独立使用时才抽成可定位的候选。

| 对象 | 专业含义 | 必须能关联什么 |
|---|---|---|
| Source / Evidence | 仓库和完整 SHA、位置、原始测试/日志/差异及获取条件 | 具体主张、版本、覆盖/未读取范围 |
| Fact | 特定版本实际代码结构、业务表现、可观察行为或声明事实 | 直接证据；声明与实际实现分开 |
| Episode | 一个问题或能力跨提交、分支、Issue、ADR 的因果事件 | 引入、修订、修复、回归与竞争解释 |
| Finding / Mechanism | 完整机制、不变量、限制、风险、替代方案及质量评价 | 支持证据、反例、适用条件和来源边界 |
| Candidate | 可迁移的语义、契约、架构/程序机制、测试或失败经验 | 原机制、目标任务、使用方法、许可证和状态 |
| Resource | 可实际使用的接口、测试向量、示例、工具或适配代码 | 使用契约、依赖、维护源及验证方式 |
| Consumer / Outcome | 确实接收知识的任务、工件和测试/结果 | 采用决定、目标版本、行为证据与反馈 |

## 3. 两个正交维度：专业覆盖与知识性质

**专业覆盖（研究什么）**：产品/功能/用户；业务能力与角色/对象/状态/动作/规则；系统/技术/部署架构；接口/算法/类/调用链/运行时；数据/安全/集成/兼容；质量/故障恢复/测试；工程过程/演进历史与决策。重要机制可跨多个维度，不按包目录推断业务或按六份报告切断关联。

**知识性质（能主张什么）**：事实恢复 → 机制解释 → 有条件评价 → 复用候选 → 实际资源 → 使用反馈。它们不是同一成熟等级的标签，也不规定每条纯理论知识都必须获得生产收益才有研究价值。

对跨主题术语要明确同名异义和不同名称的同一概念。特别区分：业务岗位、流程角色、授权集合、Agent 执行身份与组织/租户；ObjectSchema 数据对象与业务实体；Action、Command、Rule、Policy、Workflow、Lifecycle。

## 4. 研究深度、证据成熟度与工程质量

### 4.1 专业研究的深度

- **A 事实恢复**：完整问题范围内的功能、用户、对象、Schema、调用者、实现位置、测试、真实未知。
- **B 机制解释**：目标/约束、结构及动态行为、权威与不变量、状态/数据流、异常、并发、事务、恢复、历史原因（有证据才可断言意图）、替代方案。
- **C 知识迁移**：适用/不适用场景、目标技术栈与系统位置、实现使用方法、输入输出、依赖、许可、负面经验、测试/维护与潜在成本。

A/B/C 是研究内容深度，不是测试已经执行。证据的 G0–G5 状态定义与使用限制由 METHOD.md 管理，不能将“报告写到 C”误写为“已验证使用收益”。

### 4.2 评价坐标

以 ISO/IEC/IEEE 42010 的利益相关者/关注点/视图/关系、ISO/IEC 25010 的质量属性、ISO/IEC/IEEE 29148 的需求可验证性、15289 的信息项职责、12207 和 15288 的生命周期活动及相关专业方法为评价坐标。

标准适用范围和官方版本须核验；不以模板完整或某些条款标题推断符合性、合规认证。每次比较采用**同一个真实问题、约束、质量属性与证据强度**，允许上游或我们的原设计被反证。

## 5. 如何开展深入研究：横向全景与纵向事件/机制双路并行

**横向系统恢复**：固定快照；归纳产品定位、功能类型、用户、业务模型、协议分层、模块依赖、数据和部署边界、测试与质量；据此维护功能 → 定义 → 实现/消费者 → 测试 → 状态 → 缺口的能力地图。

**纵向机制与历史审查**：选真实用户任务或跨模块能力；由应用/接口入口追到契约、身份与授权、执行、状态变化、驱动/存储/副作用、错误/恢复、调用者和测试；关联 ADR、Issue、Git 历史，区分代码变化与作者意图；记录正反质量影响和重复修复的根因候选。

两路可交替：不能“先全量扫描数万文件才深入”，也不能研究少数熟悉的类就宣称系统全貌。必要时用针对性构建、调试、E2E 或角色/异常测试消除未知；未运行则明确保持静态判断。

初始深挖候选：Object Schema → 元数据编译/验证 → ObjectQL 数据操作 → 身份/记录与字段授权 → 驱动/数据副作用；是否选择此链，以首批横向证据确认真实消费者和价值后调整。

## 6. 成果层次及相互关系

1. **六份研究主报告**：产品功能、技术/程序架构、关键调用链、Java 横向比较、DES-ARC/前后端差异、现有设计反向审查。职责见 README；可分期渐进，不能先造空文件。
2. **可独立定位的知识候选**：具体业务规则、重要契约、实现机制、算法、风险反例、历史失效路径、测试方法。可放入对应报告的专节或紧凑索引；只有多任务消费者需要时才拆分为独立可引用资源。
3. **实际可用工程资源**：可运行代码/适配、协议/契约、测试向量、检查方法、示例、工具入口；有目标消费者和版本、许可、依赖、失败边界、验证方法才称为可用候选，生产采用需另核。
4. **索引与来源**：保留以稳定 commit、符号、测试、Issue/ADR 和动态版本影响为核心的来源定位；索引只是路由，不复制正文。

研究成果的职责与用途由本 DESIGN 统一解释，文件身份/模板在 README、TEMPLATES；文档类型不是独立运行时对象。知识可复用不必然等于可以复制原代码。

## 7. 快速消费设计：从研发任务反向找到可信知识

**触发**：出现需求澄清、功能设计、架构裁决、编码前置、故障/性能问题、测试方案或知识学习任务时，在任务专业语义和高风险约束下检索相关成果；普通小任务不强制全库研究。

**检索与判断**：问题/对象/动作/状态/机制/语言/质量属性匹配 → 找到候选与来源版本 → 核对适用前提、已有权威契约与未证实部分 → 选择直接采用、改造使用、参考比较、拒绝或待验证。

**交给目标任务**：提供“要解决的任务、推荐做法与不适用条件、精确来源、输入输出/依赖、必要测试、版本/许可、维护责任、待决定事项”；不直接推送为强制规则。消费者在其目标工件和测试中实际采纳后，才能登记为“已采用”。

**反馈**：目标行为错误、来源升级、设计反例、兼容问题、投入成本和实际效果反查候选及受影响消费者。只对已受影响结论作重核；没有可靠对照时不得量化节约工时。

这套消费接口**先用 GitHub + Markdown + 精准引用 + AI 检索**，不预先搭平台、数据库、独立 Agent 流水线或为每条知识制作 Skill。已有分析利用/产品仓库若有职责入口，知识归位优先用其权威维护位置；避免两边形成可独立修改的第二份正式契约。

## 8. 版本、历史、记忆与上下文恢复

不同的“记忆”必须由正确的持久位置承担：

| 需要保存的内容 | 唯一主要责任位置 |
|---|---|
| 为什么采用某种研究结构，哪些假设被推翻 | DESIGN.md 的“设计决策与修订记录” |
| 当前阶段、任务顺序、成果与下一动作 | PLAN.md 的“执行接续与事件记录” |
| 源代码和资料的版本、出处、读到/未读、证据边界 | BASELINE.md；成果具体证据在报告 |
| 研究方法、证据等级和质量审查规则 | METHOD.md |
| AI 执行时怎样读、写、复核和中断恢复 | AGENTS.md |
| 研究成果呈现与可迁移知识的最小结构 | TEMPLATES.md |

ChatGPT 记忆或过去聊天摘要**不能替代 Git 中可获取的源事实与计划**。重启时按 README → DESIGN 的当前裁决 → PLAN 的最新接续 → BASELINE 的准确来源 → 对应报告/源码恢复。离开前更新真实发生的变更与未决事项；正常执行中的重复过程不必逐轮写长日志。

Fork 同步上游须记录新 commit 与差异影响：哪些功能/契约/机制/结论受影响；旧快照与历史结论不可被静默抹去，不因同名文件变更而自动宣称所有报告失效。

## 9. 系统质量门槛与反向审查

- **专业覆盖**：重要业务/角色/功能、静态结构、动态行为、数据/安全、历史与工程生命周期有实际来源或明确的缺口，不拿扫描文件数量代替覆盖。
- **因果与关系**：描述对象→契约→执行→状态/结果→异常→测试；区别真正的作者动机与代码差异的事后推断。
- **真实验证**：文档声明、实现存在、测试代码、执行通过、运行观测、目标工程收益互不替代；每个关键主张应可反驳。
- **迁移适用性**：Java 生态与现有设计都以相同问题、条件及质量属性审查；不“搜索支持自己设计的代码”，也不因上游成熟就盲从。
- **维护成本**：报告正文、候选知识、正式契约和目标实现各有所有者，不因文件越多便算质量提高。
- **运行对抗**：正常/异常/越权/并发/版本变化/错误来源/断开的调用链/无法访问源/已被淘汰机制，必要时实际测试。
- **能力有效**：目标任务能找到、理解并使用，实际工件/测试有变化，验证结果回到知识；不能以“写了规范或 Skill”代替生效证明。

在进入 P1 后，用一条完整机制链进行**贯通检查**：从研究入口到源事实、深入机制、产生知识、模拟任务消费以及必要的真实测试。演练时“研究报告成立”与“工程使用收益”分别报告。

## 10. 当前设计决策与仍待验证的假设

| ID | 当前设计判断及理由 | 性质 / 条件 |
|---|---|---|
| D-01 | Fork 中原始文件（含 AGENTS、ARCHITECTURE）全部保留作为上游资料；研究成果独立于 research/ | 已作为研究边界实施；工具的 AGENTS 实际继承行为**未验证** |
| D-02 | 采用“总体设计 + 执行计划 + AI 指令 + 方法/模板 + 来源基线”而不是六篇报告代替研究体系 | 设计判断；其工程有效性待真实批次检验 |
| D-03 | 系统全景与纵向机制/历史交替；第一批可先研究对象读写权限链 | 候选选择，若消费者证据不足可调整 |
| D-04 | 报告、可复用知识、可用资源和生产采用保持不同性质与权威 | 设计边界，后续用真实目标任务验证 |
| D-05 | 先利用已有 GitHub、测试、Markdown 和 AI 检索；不建立新知识平台或每条知识的 Skill | 当前经济性判断，可由检索失败/规模变化推翻 |
| D-06 | 研究深度 A/B/C 不替代证据成熟度 G0–G5，更不等同于 P0–P5 阶段完成 | 防止证据越级的关键约束 |
| D-07 | 优先从历史问题和反例提取可迁移规律；但未知不能断言为缺陷或根因 | 来源判断，在具体事件链上验证 |
| D-08 | 现有 DES-ARC/SEM 与外部开源平等接受评价；历史 L0/L1 不充当现行裁决依据 | 需要取得最新正式来源才能给出真正差异结论 |
| D-09 | 未经测试的研究治理能力只能声明“已记录/设计”，不能声明 IDE 已生效或工程收益已获得 | 实际 AI/IDE 生效检验仍待执行 |

## 11. 修订与恢复纪律

- 每次重要修订记录“旧判断 → 新证据 → 新判断 → 受影响的计划、报告和消费者”，不复写历史成始终正确。
- **2026-11-15 第一轮审查**：发现六文件重“研究事实/质量规则”，轻“知识产物/工程消费/反馈”；决定补强复用与消费。
- **2026-11-15 第二轮审查**：发现没有总体设计，六份报告分类被过早当作完整体系；决定本文件承担对象关系、双路研究、知识转化、消费、演进与职责对齐。
- 本轮设计未经真实工程消费者验证；第一次批次完成后必须回看 D-01～D-09 的成立条件，必要时更正或废止。
